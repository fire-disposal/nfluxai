# 项目问题与弊端分析（2026-03-31）

> 目标：从可维护性、稳定性、安全性与一致性角度梳理当前仓库的风险点，并给出可落地改进建议。

## 1. 高风险问题（建议优先处理）

### 1.1 配置文件中存在明文密钥风险（已修复为占位）
- 现象：`config.yaml` 原先将 LLM、Embedding、Rerank 的 `api_key` 直接写死。
- 风险：
  - 一旦仓库泄露，将导致 API 额度与数据安全风险。
  - 无法区分环境（开发/测试/生产）密钥，运维不可控。
- 建议：
  - 所有密钥只通过环境变量注入。
  - CI 增加 secret scanning（如 Gitleaks）。

### 1.2 启动文档与项目结构不一致
- 现象：README 中给出 `bash start.sh`，但仓库缺少 `start.sh`（此前测试也失败）。
- 风险：
  - 新用户无法按文档成功启动，降低可用性。
  - 自动化测试会误报“结构缺失”。
- 处理：补充 `start.sh` 作为统一启动入口，优先 `uv`，回退 `python`。

## 2. 中风险问题

### 2.1 检索器初始化阶段耦合“重自检”
- 现象：`NursingRetriever.initialize()` 在启动时同步做 embedding/rerank/llm 三类外部服务自检。
- 弊端：
  - 首次启动耗时高，且受网络波动影响大。
  - 即使用户只想检索，也会被 LLM 健康检查拖慢。
- 建议：
  - 改为“按需初始化 + 延迟健康检查”。
  - 健康检查放到后台线程或管理端按钮触发。

### 2.2 错误处理策略偏“打印日志”，缺乏分层错误模型
- 现象：很多失败分支仅 `print(...)`，用户侧提示与可观测性不足。
- 弊端：
  - Streamlit 页面难以区分“配置错误 / 网络错误 / 限流错误”。
  - 运维日志难统计根因。
- 建议：
  - 定义统一异常类型（ConfigError / UpstreamTimeout / AuthError）。
  - 在 UI 层显示可执行修复建议。

### 2.3 测试脚本粒度偏“集成验证”，缺少单元测试与回归保障
- 现象：`src/test_flow.py` 是脚本式检查，不是标准 `pytest` 单元测试。
- 弊端：
  - 难以在 CI 中做细粒度回归定位。
  - 对边界条件（空文档、异常 API 响应）覆盖不足。
- 建议：
  - 新建 `tests/`，拆分词典识别、配置加载、响应解析单元测试。
  - 对 `ApiReranker.rank` 增加返回格式参数化测试。

## 3. 低风险但长期影响的问题

### 3.1 README 与实现存在历史漂移
- 现象：README 仍包含部分旧描述（例如目录示例与现状存在出入）。
- 弊端：
  - 新成员认知成本增加。
  - 文档可信度下降。
- 建议：
  - 建立“文档变更随代码 PR 同步更新”的检查清单。

### 3.2 代码路径注入方式较粗放
- 现象：多处通过 `sys.path.insert(0, ...)` 解决导入。
- 弊端：
  - 在不同执行入口下容易出现模块解析歧义。
- 建议：
  - 采用标准包布局（如 `src/nflux_ai/...`）并以模块方式启动。

## 4. 优先级行动计划（建议）

1. **安全基线（本次已落地一部分）**
   - 移除明文密钥，统一环境变量注入。
2. **稳定性基线**
   - 初始化流程改为懒加载，减少启动阻塞。
3. **工程化基线**
   - 补齐 pytest + CI，替代脚本式“人工看日志”验证。
4. **体验基线**
   - 对常见错误给出分级提示与恢复建议。

## 5. 本次审查结论

项目已经具备可运行的 RAG 问答主干能力，但在**安全治理**与**工程化可维护性**方面仍有明显短板。若要面向团队协作或生产化演进，建议按“安全 > 稳定性 > 自动化测试 > 体验优化”顺序推进。
